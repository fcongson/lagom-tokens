# Token sources

Tokens are written in the [W3C DTCG](https://www.designtokens.org/tr/drafts/format/) format (`$value`, `$type`, `$description`), as [Tokens Studio](https://tokens.studio/) multi-file sets: one folder per brand, one file per set. [`$metadata.json`](./$metadata.json) gives Tokens Studio the set order.

```
tokens/
  base/       MIT: the contract and the Base brand
  fern/       all rights reserved
  waypoint/   all rights reserved
```

## Sets

Each brand folder can have:

- `palette.json`: the brand's colour ramps, generated by `scripts/ramps.js` from the anchors in each family's `$extensions["lagom.anchors"]`. Edit the anchors, then run `yarn ramps`.
- `core.json`: type, spacing, radii, and other primitives.
- `semantic.json`: roles in light mode. **Base's `semantic.json` is the contract**: every role, with a `$description` saying what it's for and what contrast it must reach.
- `semantic-dark.json`, `semantic-more.json`, `semantic-more-dark.json`: only the roles that change in dark mode, increased contrast, and both.
- `component.json`: component tokens, which reference roles.

## How a brand is built

For each variant (light, dark, more, more-dark), a brand's tokens are Base's sets followed by the brand's own, in the order above, later sets winning. So a brand only needs to define what differs from Base.

Palettes are namespaced per brand. In Fern's files, `{palette.olive.45}` means Fern's olive; it becomes `--fern-olive-45` in CSS. Base's roles always point at Base's palette, so a role a brand doesn't override can never pick up another brand's colour.

## Rules `check-brand` enforces

- A role a brand overrides in light it also overrides in dark, and the other way round.
- Every role resolves in every variant.
- Every pair in the contract passes contrast: AA normally, AAA with increased contrast, and `fg-default` on `bg-default` at 9:1 or more (the three-band focus ring over images needs it).
